# Security

## The library and the browser core

- No network calls of any kind, in Python or in the browser core. The parity test refuses a core that mentions network, DOM, storage or eval calls.
- No eval, no `new Function`, no pickle, no shell calls. Assembly formulas are read by a small hand-written parser (numbers, `+ - * / ( )`, the measurement totals, the assembly's own inputs and nine named functions); anything else is refused with the reason, and formulas are capped at 500 characters, 200 tokens and 40 levels of nesting.
- Markup files are parsed as JSON and rebuilt field by field (FORMAT.md lists every rule): known keys only, ids limited to letters, digits and `_.:-` (and never `__proto__`, `constructor` or `prototype`), text trimmed to a cap with control and bidirectional-override characters removed, coordinates finite and within 10 million points, at most 100,000 markups, 20,000 points per shape, 200 cutouts, 500 comments per markup, 500 layers and 2,000 assemblies. A bad markup is skipped and counted; the rest of the file still loads. Files over 50 MB are refused.
- Merging a teammate's file goes through the same cleaning, then compares version histories; nothing from the other file is trusted beyond what a markup file may hold.
- CSV exports prefix any text cell that starts with `=`, `+`, `-`, `@`, tab or carriage return with an apostrophe so spreadsheets do not run it as a formula. The XLSX writer stores values only: no formulas, macros, external links or shared strings from the input; text is written inline (so it is never read as a formula), and a text cell that starts with one of those characters also carries the quote prefix style, so editing it in a spreadsheet program keeps it text. A test reads the workbook back with openpyxl and checks for external link parts and external relationship targets.
- Imports are read by small parsers of our own: a PDF object reader for tool chest items (depth and size capped), an XML reader that refuses any document type declaration or entity (so no external entities and no entity expansion) and reads each tag's attributes in one linear pass (a long tag cannot stall it), and a CSV reader capped at 100,000 rows. Keys named `__proto__`, `constructor` or `prototype` are dropped by every reader (PDF dictionaries, XML attributes, summary columns). Compressed tool chest items are inflated as a stream that stops at 4 MB per item and 64 MB per file, so a small zlib bomb cannot fill memory. Size caps: tool chests 20 MB (`.btx`) and 2 MB (JSON), price lists 20 MB, markup summaries 50 MB, assemblies files 4 MB. Seeded fuzz tests (`tests/js/fuzz.test.mjs`) feed every reader and the live session checks thousands of hostile inputs.
- The CLI reads only the markup file named on its command line (capped at 50 MB) and writes to standard output.

## The browser app

### One way out, four switches, all off

Every request the page could make passes through one gate, `net()` in `web/src/ui/12_net.js`, and every peer connection through `netPeer()` beside it. A test checks that `fetch` appears only inside the gate and `RTCPeerConnection` only inside `netPeer()`. There are four network switches in Settings, and all are off until the person turns them on:

- **OCR** allows exactly one outside address: the English language data for text recognition, `https://cdn.jsdelivr.net/npm/@tesseract.js-data/eng@1.0.0/4.0.0_best_int/eng.traineddata.gz`. The gate refuses any other URL, sends no cookies or referrer, refuses redirects, and the download is checked against its pinned size and SHA-384 (`sha384-JI+fraGAoc5GBGIliuqzHRnP1nJyrukg5ggNSBv/TO+YOVj+6Te6XXQOx7ia10xq`) before it is kept on the device, and again each time before it is used. Recognition itself runs on the device, in a worker: the engine (tesseract.js-core 6.1.2, Apache 2.0, the LSTM WebAssembly build) is embedded in the single-file page; the Pages build keeps its WebAssembly in a file of its own next to the page (`docs/tesseract-core-lstm.wasm`, 2.7 MB), which the same switch lets the gate fetch from the same site, once, by its exact address. Either way the engine is checked against its pinned SHA-384 before it runs, and a copy that does not match is refused (a test serves an altered one).
- **Live session** allows peer-to-peer connections (WebRTC data channels, encrypted by DTLS). With no STUN host set in Settings, the peer connection has no ICE servers, so no server is contacted at all, and only local network candidates are kept in both directions: host candidates on hidden mDNS names or on addresses that are not globally reachable (private, shared, loopback, link-local and documentation ranges, IPv6 link-local and unique local). Server-reflexive, relay and peer-reflexive candidates and any public address are removed from the offer we send and from the one we receive, so a code cannot point this device at an outside host. Joining is by copying a code, or scanning a QR code drawn on the device. A STUN host, if the person sets one, sees connection addresses only. Live sessions need a secure page (https or this device) because the PDF check and the session fingerprint use SHA-256.

- **AI on this device** lets the gate load one module, the WebLLM library at its exact pinned address (`@mlc-ai/web-llm@0.2.84/lib/index.js` on cdn.jsdelivr.net), which the Pages build's import map also pins by SHA-384. Every file of the model then comes through `net()` from an exact allowlisted address and is checked before it is used: the model library from raw.githubusercontent.com at a fixed commit, by SHA-384; the model's own files (Qwen2.5 1.5B Instruct, 4-bit: `mlc-chat-config.json`, `tokenizer.json`, `tensor-cache.json` and 30 weight shards, 875,705,761 bytes) from one immutable revision of its huggingface.co repository, `9bd564b064631febf14deadcac492efb761d60c3`, named in every address (never `main`), each by its size and by the hash the repository lists for it: SHA-256 for the weight shards (their LFS object ids) and the git blob id (SHA-1 of `blob <size>\0` and the bytes) for the three JSON files git keeps directly. The pins are in `web/src/core/27_providers.js`; they were read from the repository's API for that revision on 2026-10-22 and agreed across three separate reads. A file that does not match is refused and never kept. Checked files go into the browser's cache under the addresses WebLLM reads, and a copy already there is checked again before each load, so WebLLM finds everything it needs there and makes no request of its own. The repository answers a weight file with a redirect to its file store; `net()` follows redirects for this switch only, and only to huggingface.co and hf.co hosts. The model runs on the device (WebGPU); without WebGPU the app says so and loads nothing. Delete all data also removes the model's files.
- **AI with your own key** works with any service with an OpenAI-compatible chat completions API, or a model server on this computer. The person types its base address, the model id and the key. The gate then reaches exactly one address, that service's chat completions endpoint: https to any host, or http only to localhost and 127.0.0.1; no user name, password, query or fragment is accepted in it, and nothing else is allowed under this switch. The key is entered in Settings and kept in memory, or on this device in IndexedDB when the person ticks that; it is never put in exports, markup files or the grounding pack. Before any request the app shows the request exactly as it will be sent (address, headers with the key masked, the body byte for byte, its size in bytes); nothing goes until Send. When the model asks for tools, each round of their results is shown the same way, with the calls it asked for, and needs its own Send. Every request starts from a click. The PDF goes only when the person ticks it for that question, and only with the question itself. The service's error message is shown with the key (and its first or last characters) removed.

The headless tests record every request while they use the app with every switch off, opening the OCR and live session prompts, help, the library and every export, and fail on any request that is not the page itself, its fonts, icon or manifest. They also check that no peer connection is made.

### Policy

The Pages build sends a Content-Security-Policy with `default-src 'none'`, scripts only by hash plus `'wasm-unsafe-eval'` (WebAssembly compilation, used only by the text engine; JavaScript eval stays off; the engine's worker is built from a blob and takes the page's policy, so the allowance has to be on the page), `connect-src` set to `'self' https: http://localhost:* http://127.0.0.1:*`. The policy cannot name the address of a service the person types in, so it fences connections to https, this site and a model server on this computer, and the network gate (`net()` in `web/src/ui/12_net.js`, the only place the page calls `fetch`) decides each request: only with its switch on, and only to that switch's exact addresses (the pinned OCR data, the pinned model files at their fixed revision, with redirects only to huggingface.co and hf.co hosts, and the one service address set in Settings). With every switch off the page makes no request at all, which a headless test checks, `script-src` adding only the pinned model library's exact address (an import map pins its SHA-384), workers only from `blob:` (the PDF engine, the render worker, the image worker and the text engine are all built from the page's own embedded code), no forms, frames or objects. Fonts are served with the page.

### PDFs

- PDFs are untrusted. pdf.js (5.7.284, the ES module build, Apache 2.0) opens them with `isEvalSupported: false` and XFA off, from bytes in memory (no URL fetches), in a module worker started from a blob. That setting closes the font matrix injection in pdf.js before 4.2.67 (CVE-2024-4367) on its own; the embedded version also carries the upstream fix, and the policy has no `unsafe-eval` as a third wall. A test builds a PDF with the injection, shows that it runs in the vulnerable pdf.js 3.11.174 (a dev dependency used only by that test) when eval is allowed, that it does not run in the embedded engine even with eval allowed, and that it never runs in the app.
- Sheets are drawn in a second worker that runs its own copy of the same embedded pdf.js with the same options, on an OffscreenCanvas. It gets a copy of the PDF's bytes (never shared memory) and returns pictures.
- PDF JavaScript, open actions, form actions and links never run: the app draws annotation appearances as pictures and has no annotation layer, form layer or script engine for PDFs. Opening a PDF is capped at 500 MB and 5,000 pages, times out after 60 seconds, and a file without a `%PDF` header is refused before parsing. Tests feed the app garbage, truncated files, a million-page lie, 5,001 real pages, a 200 x 200 inch page, absurd nesting and a file with scripts in every place a viewer might run them.
- Reading markups from a PDF's annotations (pdf-lib, 1.17.1, MIT) turns each annotation into plain values with depth and size caps, then into a markup through the same cleaning as a markup file. Only markup and measurement subtypes are read; links, widgets, files and scripts are left alone.
- Reading markups from a PDF's annotations and writing them back as annotations both run in a worker, not on the page. Before pdf-lib loads the file (it unpacks every object stream on load), every object stream is found in the raw bytes and unpacked with a byte limit: more than 20,000 streams, a stream claiming more than 100,000 objects or 2,000,000 in all, a stream that unpacks past 64 MB, past 1,000 times its packed size beyond 16 MB, or streams past 512 MB together, and the file is refused with a plain message (a test opens an 80 MB compression bomb). A worker that still runs out of memory, or works for more than two minutes, is stopped and the page carries on.
- Writing a PDF (flattened, or with markups as annotations) uses pdf-lib on a copy and removes the document open action, document additional actions and document-level scripts; the copy with annotations also drops page and annotation additional actions, form field triggers, any XFA form, and every JavaScript, launch, form submission, import, reset, media and remote go-to action on the annotations it keeps (links to pages and web addresses stay). The annotations written carry no actions. A test writes annotations into a PDF with scripts in every place a viewer might run them, checks with qpdf that the result is a valid PDF and walks every object to confirm no script or action is left. The original file is never changed.

### Live sessions

- Peers are untrusted. Every inbound message is checked field by field (`peer_message` in `web/src/core/21_peer.js`): a known message type, ids, names and text within their caps, coordinates within the page, pages that exist, markups through the markup file's cleaning. Messages over 1.5 MB are dropped, each peer has a token-bucket rate limit per kind of message (unknown types share one small bucket), and a peer that keeps sending bad messages is disconnected. A peer says hello once; only the host may send the roster or lock the session; guests accept connection signals for other guests only when the host relays them, and the host relays a signal only from the guest it names as sender; no one can join under an id already in the session. Session codes are inflated with a 100 KB cap. A headless test has a hostile host send malformed, oversized and prototype-keyed messages, HTML in every text field, floods and fake rosters, and checks that the guest shows text as text, keeps its settings, keeps working and disconnects the peer.
- The PDF never leaves the device. Peers send the PDF's SHA-256 when they join; if it differs, the app says so and nothing is exchanged with that peer until both open the same file.
- The session fingerprint (from the DTLS certificate fingerprints in both offers) is shown as groups of digits on every device, so people can read it to each other and confirm no one sits between them.
- At most 8 people per session (a full mesh). The host can lock the session: then only the host's changes are shared. The host can also set "Guests can edit only their own markups": every device then refuses, on receive, a guest's change or deletion of a markup whose author is not that guest (a name two people in the session use belongs to no one), and a guest's own app keeps such changes local and says so. A test has a guest's app send another person's markup under its own name and a deletion, and checks the host keeps the original.
- A merge that would leave more than 100,000 markups (the file's limit) stops before merging, with a message, so nothing is dropped when the file is next opened.

### Plan questions and models

- Drawing and document text is data, never instructions. In the grounding pack every text line is cleaned (control characters, bidirectional and zero width marks, fillers, variation selectors, Unicode tag characters, which a model reads and a person never sees, and lone surrogates removed; the words that fence the data block removed), capped and placed inside one fenced data block after the rules; lines that read like instructions to a model are flagged as such in the pack. Tests put hostile text in a title block and in a project manual (orders to ignore the rules, call tools, reject every markup, send the PDF and the key to an outside address) and check it stays inside the data block.
- The model can only call an allowlist of tools (quantities, find markups, find text, sheets, estimate, and the proposals show, propose markups, set status and make a filter), each with strict arguments: unknown tools, unknown arguments, ids that do not exist, points off the page and unknown statuses are refused. Tools that would change the takeoff return a proposal; it changes nothing until the person clicks it, and each click is one undo. The text of a proposal (a markup label, a filter) has links and HTML removed. No tool deletes, sends, opens or fetches anything, and none touches settings. Tool results sent back to the on-device model sit inside the same data fence. A headless test opens a plan set whose title block gives orders and has a mocked model obey them (set every markup Rejected, propose markups and a filter carrying an outside address, call a tool that does not exist, answer with an image link, raw HTML and invented numbers) and checks that nothing changed, no settings moved, nothing was fetched from the address, every request shown was byte for byte the one sent, and the invented numbers were marked.
- Answers are plain text shown with `textContent`. Links and HTML are removed from them, citations that name no markup or sheet are dropped, and every number must equal a number value a read tool returned for that question (exactly, or rounded to whole units, tenths or hundredths). Digits in drawing text, labels, the pack or a proposal never count, digits run into units (1200LF) are checked like any other, full width digits are read as plain ones and digits of other scripts are always marked, and the set's sheet numbers and scale notes are names, not numbers. Numbers written in words (twelve, one hundred and five) are checked by their value the same way. Any other number is marked [?] and listed. The plan review summary keeps only suggested RFIs that cite real findings, and the project manual check keeps only answers that name a section the manual has.
- All prompts and tool definitions are in the repository (`web/src/core/26_ask.js`, mirrored in `src/plantakeoff/ask.py`); the request format for the AI service is in `web/src/core/27_providers.js`. The service is mocked in the tests, as a hosted https address and as a server on localhost; no test contacts a real service.

### Text recognition

- The language data is fetched only behind the OCR switch, only from its one address, and only kept when its SHA-384 matches; a test serves altered data and checks it is refused. The engine and its data run in a worker; recognized text is kept in the device cache for that PDF and only feeds search, the title block reader and the sheet index.

### Shared folder sync

- Uses the File System Access API on a folder the person picks. The app writes only its own file there (`<plan set>.<author>.markups.json`, a name made from letters, digits and dashes) and reads the others as teammates' markup files, through the same cleaning and merge review as any markup file. It reads only plain files directly in that folder (never subfolders), at most 64 per pass and 50 MB each; a file that cannot be read, is too large or is not a markup file is skipped and tried again only when it changes, and only files made for the same PDF (by SHA-256) are merged. Where the API is missing, Merge markups from a file does the same by hand.

### The page

- The GitHub Pages build refuses to run inside another site's frame (Pages cannot send a header that forbids framing, and a meta policy cannot set `frame-ancestors`): a framed page shows only a notice with a link that opens the app in its own tab, so a hidden frame cannot be used to trick clicks such as Delete all data. A headless test loads the page in a frame to confirm it never starts or opens storage.
- All user text reaches the page through `textContent` or attribute values; there is no `innerHTML`, no `eval`, no `new Function`, no inline event handlers, no `alert`, `confirm` or `prompt`.
- Plan files, markups and caches stay on the device in IndexedDB: markups autosave, a copy of each opened PDF is kept so it reopens after a reload (Settings can turn that off), and a cache holds page text, recognized text and thumbnails per PDF (trimmed to a cap). localStorage holds no user data. Settings, Delete all data cancels any pending autosave, detaches storage so the open plan set cannot be written back, clears every store, deletes the database and the app's localStorage keys, then reloads. The offline cache holds only the app's own files. A headless test deletes right after an edit and checks that nothing is left.
- Embedded libraries (pdf.js and its worker, pdf-lib, the text engine and its WebAssembly) are copied from npm by `tools/vendor.py`; the build refuses to embed or publish a file whose SHA-384 differs from its pinned value in `web/vendor/pins.json`, and a test checks the embedded copies and the Pages build's separate engine file again.

## Reporting an issue

Open a GitHub issue titled "Security" with a description and steps to reproduce. For anything sensitive, use GitHub's private vulnerability reporting on this repository instead of a public issue.
